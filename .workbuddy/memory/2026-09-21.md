## Bug 修复：留言板回复楼层顺序错乱

现象：回复的「N楼」编号没有按先后排列。

### 根因（两个函数互相叠加）
1. **楼层号取自 map 下标**，而 `cs` 是 `(p.comments||[]).filter(...)` —— 即**数组插入顺序**，不是时间顺序
2. 只有 `scheduleBoardComments`（彼回复）末尾做过一次 `sort by ts`（还是虚拟 ts）；
   `sendBoardComment`（**我**回复）push 后**压根没排**，所以它永远占着数组末尾
3. 时间轴混用：我的回复 `ts = Date.now()`（真实），彼的回复 `ts` 是 `_nextBoardTs()` 生成的**虚拟未来时间**
   → 我刚发的真实时间会被排到彼那些"未来"回复**之后**，看起来像插队到最上面

### 修复（统一两条时间轴）
- 新增 `_cmtRealTs(c) = c.arriveAt || c.ts` —— 彼的按到达时刻、我的按发送时刻，同一条真实时间轴可比
- 新增 `_commentsOf(post)`：渲染前统一 `sort(_cmtRealTs)`，**所有读取入口都走它**
  （`renderBoard` / `renderBoardDetail` / `scheduleBoardComments` 的引用池 slice(-3)）
- `sendBoardComment` push 后也按 `_cmtRealTs` 排一次（双保险，存库即有序）
- `_lastTsIn(post)` 改为取 **`Math.max(ts)`** 而不是 `cs[cs.length-1].ts`
  ← 原来我插在末尾的真实时间回复会把下一条彼回复的虚拟时间锚点**拽回过去**

### 实测（脚本验证）
- 场景：彼甲(+15s到) / 我乙(+20s) / 彼丙(+40s到)，彼两条是一次 schedule 先入库的
- 修复前：1楼甲 2楼丙 3楼乙 ✗ → 修复后：1楼甲 2楼乙 3楼丙 ✓
- 楼层号稳定：先到的不会被后到的挤动（+16s 显示 1甲2乙，+41s 仍是 1甲2乙3丙）
- 时间锚点取到最大值（丙），不再倒退

### ⚠ 记住的教训
这个 App 里**到处是双时间轴**：`ts` 可能是虚拟的（彼的内容），`arriveAt` 才是真实发生的时刻。
凡是要排「先后顺序」的地方，必须用 `arriveAt || ts`，不能用 `ts`，更不能靠数组插入顺序。

## 组字（genRecomb）本次新增的两张内置表

1. **意象 / 时间 / 处所槽位** `{i}{t}{p}`（`RECOMB_IMAGES` 20 / `RECOMB_TIMES` 14 / `RECOMB_PLACES` 16）
   + 8 条带这些槽的模板。**刻意不放进 Markov 链**（它们是名词，灌进链只会反复冒同一批词），
   走槽位每次只出一两个，像随手拈来的场景。
2. **句尾收束** `RECOMB_TAILS`（45% 概率）：`……` 写了三遍做加权 —— 因为 Markov 走到目标长度是**硬停**，
   常常断在词中间（"我在月亮里想起"），省略号接得住；只在句尾无标点时补。

实测（27 张假字卡跑 30 句）：意象命中 18/30、句尾收束 14/30、生成失败 0。

## ⚠ 发现但**尚未修**的质量问题（下次可接着做）
`_buildMarkov` 里 `idx.frags / idx.segs` 是 `seg.substr(随机位置, 随机长度)` 的**任意子串**，
会把词切碎 → 长句拼段和模板填空出来的东西带语病：
```
到很远的时候，终年不 / 时的勇气的时候 / 影子留在车站在啊。
忽然之间就长大了，忽然之间就长大了，…（同一片段重复出现）
```
根因：没有分词器，切点不看词边界。
修法候选：只在「子句开头」或「功能字之后」（的/了/在/和/就/把/被/到/着/过…）取起点，终点也尽量落在边界。
  - 不用晚于上一条 ❌（可以「早上」排在「傍晚」后面）
  - 不用避开深夜 ❌、不管现在几点 ❌
  - 不跨天 ❌
- 楼层先后永远由 `arriveAt` 决定，时刻乱序**不影响**任何排序 → 所以上面那些约束全无必要

实现就几行（`_nextBoardTs`）：`new Date(anchor)` 拿日期 → 随机抽 `BOARD_DAY_PARTS` 一段 → `setHours(段起点+随机偏移, 随机分钟)` → 返回。
**没有** `_boardSlots`、**没有** `BOARD_MIN_GAP`（都已删除，勿恢复）

### 实测（3000 次抽样）
- 日期偏离真实当日：**0 次** ✓
- 时段名越界：**0 次** ✓
- 分布均匀：凌晨16% / 清晨17% / 早上15.6% / 中午17.1% / 下午18.7% / 傍晚15.6% ✓

⚠ 副作用要记得告诉用户：删掉"晚上"后，**19 点以后统统显示「傍晚」**。
想加回就在 `BOARD_DAY_PARTS` 的傍晚后面插 `{h:19,n:"晚上"}`（源码注释里写了）。

## 🔍 手机壳子排查（2026-09-21 19:00，总经理提出"如果是壳子的问题怎么办"）

### 已确认的事实（查过仓库，不是推测）

### 判断"是不是壳子"的最省事办法
**同一部手机、同一个链接，壳子 vs 手机自带浏览器各开一次**：
壳子慢+浏览器流畅 → 壳子问题；两个都慢 → 页面/设备问题。

→ **先推，再判断，别一上来就换壳。**

1. 查 WebView 内核版本（Android 设置 → 应用 → Android System WebView）；<80 基本可定性
2. 改壳子 WebView 配置：`hardwareAccelerated="true"`（关掉=全 CPU 渲染，最经典病因）、
   `setDomStorageEnabled(true)` / `setDatabaseEnabled(true)`、别用 `shouldInterceptRequest` 同步拦请求、
   `largeHeap="true"`；另查 `onResume` 是否重跑 `loadUrl`（每次切回来重跑 init）
3. 换成基于**系统 WebView** 的壳（别用自带内核的）
4. 不用壳 → 做 PWA（需先补 manifest + sw.js，见上）

### ⭐⭐ 关键约束：**壳子不能拆**（2026-09-21 19:04 总经理给出）
> "我试过 pwa，但是如果我再使用浏览器的时候浏览器定时清理缓存，数据也会被清除，所以我才会套壳子。"

**他的判断是对的，且技术上成立 —— 这是路线约束，不是偏好：**
- 浏览器里 `IndexedDB` / `localStorage` 属于 **origin storage，是"尽力而为"的**：
  存储紧张时浏览器会**整站驱逐**（IndexedDB + localStorage + CacheStorage 一起没）；
  只有拿到**持久化授权**（`navigator.storage.persist()` 返回 true —— Chrome 按参与度判定，
  或"装成 PWA"后自动给）才豁免。且手动清"网站数据/Cookie"照样一次清空。
- 壳子里 WebView 的数据在**应用私有目录**（`/data/data/<pkg>/app_webview/`）：
  系统不会驱逐它，"清理缓存"清的是 cache 目录不是 app 数据；只有"清除数据"或卸载才会没。
- → **壳子在存储耐久性上确实优于 PWA。PWA 不是套壳子的替代方案。**
- 补充：Chrome 清"缓存的图片和文件"**不该**动 IndexedDB（IndexedDB 归"网站数据"）。
  他上次大概率是清了"网站数据"，或被杀毒/管家类工具回收了 Chrome 空间。

# 墓碑（Tombstone）方案可行性体检（2026-09-21 20:23，用户给方案，**未执行**）

## ✅ 方案成立的部分

## ⛔ 障碍 1（最致命）：5 张表没有时间戳 → "谁新听谁的"直接失效
逐表核过创建处：

| 表 | 创建处 | 时间字段 |

| `surveyRecords` | L5671 | `ts` ✅ |

| `sounds` | L1248 | 无 |

方案代码 `const localTime = l._del || l.ts` → 对 cards/members/surveys 得到 `undefined`。
`remoteTime > localTime` 里 `数字 > undefined` = **false** → **远端永不生效**。
具体后果：A 删卡片并推送 → B 合并时 `localTime=undefined`、`remoteTime=_del`（数字）→
`false` → 保留 B 的正常卡片 → **卡片复活**。正好是墓碑要解决的问题。
→ 必须**先统一引入 `_upd`**（创建/编辑/删除都写），或判据改成
`(_del ?? 0)` vs `(_upd ?? ts ?? addedAt ?? 0)`。

## ⛔ 障碍 2：`chats = chats.slice(-CHAT_MAX)` 会物理砍掉墓碑
L3582（**每次发消息都跑**）/ L3657（手动清理）是物理截断。
墓碑留在原数组位置 → 老墓碑先被砍 → 超过 2000 条后对老消息的删除**传不出去**。
且墓碑占掉可见历史额度（`_mergeChats` 的 cap 也是按 ts 排序后切尾 2000）。
→ 截断需豁免墓碑，或 cap 只对非墓碑计数。

## ⛔ 障碍 3：字符串数组类没有墓碑能力 —— **1.14.0 的既有缺陷，方案没覆盖**

## v1.14.2 合并拉取「单向回填」—— v1.14.1 没修干净的那一半

用户反馈：**v1.14.1 之后新发的画作，跨设备后**依然是 `[画作]` 灰字气泡。

### 排查过程与结论（值得记住的推理链）

| 检查项 | 结果 |
| --- | --- |
| 本地 `_stripChatMedia` 是否保留 painter/seed | ✅ 保留（v1.14.1 已修） |
| 线上 `app.js` 是否 v1.14.1、是否还有 `delete c.painter` | ✅ v1.14.1，已无 delete |

→ **推送端没问题。** 那问题只能在**接收端**。两条候选：
(A) 接收端壳子缓存了旧 app.js；(B) 接收端已有一条**残缺同 mid 记录**，云端的完整版被卡住。

### 根因（B，已确认机制成立）

`_mergeByKey` 是**同键无条件跳过云端**：

```js
if(k!=null){ if(seen.has(k)) continue; seen.add(k); }
```

本意是「防旧数据覆盖本机」——方向对，但它顺带堵死了「**云端来补齐本机缺的媒体**」。
死锁链条：

1. 某设备在 v1.14.1 前拉过一次 → 落下 `{mid, text:"[画作]"}`（无 painter）
2. 之后无论怎么「合并云端数据」，云端那条完整的 `{mid, painter, painterSeed}`
   都因 mid 撞车被 `continue` 跳过
3. → 该设备上画作**永久**定格为灰字气泡

**「新发」也一样** —— 新发只保证**云端**有完整版，不保证本机能收下它。

### 修法：`_mergeChats` 单向回填（**不动 `_mergeByKey` 本身**）

为什么只改 `_mergeChats`：`_mergeByKey` 被 cards/members/surveys… 共用，
动它会波及所有列表类；回填只对聊天消息有意义，所以做成 `_mergeChats` 的局部特例。

| 本机缺 | 云端有 | 动作 |
| --- | --- | --- |
| 无 `painter` | `painter`+`painterSeed` | 补上 |
| 无 `image` 且无 `imgId` | `image` 或 `imgId` | 补上 |
| 无 `sticker` | `sticker`+`stickerId` | 补上 |

⛔ **绝不改写 `text` / `ts` / `sender` / `name`** —— 本机优先的初衷一点没丢。
这是 v1.14.0「同键本机优先」的**唯一例外，且方向严格单向**。

顺手：`_msgKind` 的图片判定放宽为 `m.image || m.imgId`（为 v1.15.0 铺路）。
