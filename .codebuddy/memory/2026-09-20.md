## 已实现：方案C —— 内置离线简转繁词典
- 新增生成器产出 **`s2t-dict.js`（187KB）**，`window.S2T_DICT` 为整段字符串；index.html 用 `<script src>` 引入（放 localforage 之后、app.js 之前），**不用 fetch**，故 `file://` 直接打开也能用
- 数据来源 OpenCC（jsdelivr CDN）：STCharacters.txt 3881 单字 + STPhrases.txt 35756 词组
- **核心裁剪技巧（体积 720KB→187KB）**：对每条词组计算「逐字用单字表转换」的结果 v1，只有当 `v1 !== 词组目标值` 时才保留该词条 → 35756 条只剩 **7751 条真·消歧条目**，其余 28005 条冗余（可由单字表推导）。最终 11632 条 / maxLen=4
- 词表用**空格**分隔 key/value（而非 OpenCC 的 tab），省去 JS 字符串里的 `\t` 转义，再省几 KB
- app.js 实现：`_ensureS2T()`（懒建 Map，11632 条）+ `s2t(s)`（**长词优先最大正向匹配**，最长 4 字 → 单字 → 原样保留）
- **`S2T_OVERRIDE` 人工校正层**（放解析最后无条件覆盖，优先级最高）：`吃→吃`（原表 吃→喫 会把「吃饭」变「喫飯」，已修正）、`着→著`（单字表缺 着→著，词组覆盖不到处会漏）、`皇后/太后/影后` 固定不转（无分词时对「皇后的后」无法区分）
- `cfg.tradTransOn:true` + 设置页开关 `sw_tradTransOn` + `syncUI` 同步
- 接入点选在 `_addChatMsg`：**仅对 `sender==="opp"` 且无手写 `translation` 且非图片/表情/画作/歌曲** 的消息自动生成译文 —— 一处覆盖全部回复类型，且不污染卡片数据
- 实测：28000 字转换 5ms；10 句聊天例句全部正确
- 已知保留差异（属 OpenCC s2t 正字选择，未改）：麪(而非麵)、裏(而非裡)、爲(而非為)、着→著 已补；**不含**地区用词差异（软件→軟體 属 s2twp）
- 待观察：`台`→`臺`、`后`→`後` 在缺词组覆盖时仍会误转，用户可自行往 `S2T_OVERRIDE` 追加

## 已实现：组字（Markov B + 模板 C + 退回抽卡）
用户定版：B 主 + C 兜底 / 起止无固定 / 长度 3-30 字 / 同一 n-gram 出现上限 3 次 / 只用非歌词的字卡 / 加时间复杂度限制、失败退回原抽卡
- 代码位置：`fireReply` 之前的「══ 组字 ══」区块；入口 `genRecomb()`
- **三级降级**：`_markovSentence()` → 失败 → `_tmplSentence()` → 失败 → 返回 "" → fireReply 的 `recombined` 标志为 false → 走原抽卡逻辑
- `_buildMarkov()`：语料 = `cards.filter(!shielded && cat 未被屏蔽 && cat!=="歌词库")`，**按非汉字切成子句再建链**（跨句不能建链，否则接缝会被当成合法搭配）；产出 bi/tri/chars/frags(2-4字，模板槽位)/segs(4-10字真实片段，长句重组)
- 缓存签名 `cards.length|总字数|屏蔽分类|屏蔽卡数` —— 加「总字数」是为了编辑/替换单张卡（卡数不变）也能失效
- **关键实测教训（重要）**：
  1. 硬把单条 Markov 链走到长目标会崩坏；但也不能「多段 Markov 拼接」——实测那样 avgLen 19.6、出现 44 字胡言串，**更糟**
  2. **最终方案**：`target<=12` 走单段 `_markovWalk`；`target>12` 改用 `segs`（语料里真实存在的子句片段）重组 —— 每段语法都成立，效果最接近「组字」语义。实测 avgLen=15.4、median=16、无一超过 30、500 句 5ms
  3. 曾经修掉的 bug：模板片段长度 `1+random*3` 实为 1~3 字（注释写的 2~4），导致模板句出现「我不个」；改为 `Math.min(seg.length, 2+random*3)`
- 挂接：`fireReply` 文字分支内，`if(cfg.recombOn && Math.random()*100 < cfg.recombProb)` → 生成成功则 `text=gen; trans=""; fragments=[gen]`，跳过抽卡；`trans=""` 使其能被**自动繁体译文**接管
- 配置：`recombOn:true, recombProb:15, recombOrder:3, recombMin:3, recombMax:30, recombMaxRepeat:3, recombMaxSteps:300`
- UI：设置页 `sw_recombOn` 开关 + 「组字设置」snav 入口 → `openRecombSettings()`/`renderRecombSettings()`（含占比/链阶/长短上限/重复上限/步数上限滑杆 + 「试生成一句」预览 + 语料统计）
- 时间/联防：`budget` 对象跨 twigg年开始ichéville purge 全句共享，`maxSteps` 硬上限；`_pickRecombChar` 返回 null 即停
- 注意：若后续要加原创 preview，需 `_mkCache=null` 强制重建索引

### 2c. transProb 语义变更 —— 由「是否生成译文」改为「是否以繁体为正文」（用户确认后修正）

## 组字（genRecomb）现状 —— 供后续改造参考
- 语料 = **非歌词字卡**（`_buildMarkov` 里 `cards.filter(...)`，1974 行），只在内存建索引，不写字卡
- ⚠ **只认汉字**：`RECOMB_CJK=/[\u4e00-\u9fa5]/`（1959）且 `raw.split(/[^\u4e00-\u9fa5]+/)`（1982）→ **阿拉伯数字 0-9、英文、标点全被当分隔符丢弃**，所以组字永远不出数字
- 门槛极低：`RECOMB_MIN_SRC=3` 张卡、`RECOMB_MIN_CHARS=20` 个不同汉字就能跑 → 字卡少时句子会很破碎
- 三级降级：Markov 游走(B) → `RECOMB_TEMPLATES` 的 `{w}` 槽位填空(C) → 调用方退回抽卡
- 用户问过"能否内置词典 + 数字 0-9"，已给可行性分析（**尚未实现**）。核心结论：数字建议走**模板槽位**而非进 Markov 链；内置词典若要真生效需要 n-gram 频率而非字表；**file:// 双击场景下 fetch 云端词典不可靠，只能真内置进 app.js**

## 电脑端（≥768px）适配：内容列限宽居中

用户诉求：手机端主页面一屏不滚动已"刚刚好"，电脑端还能改。

### 关键约束（不要踩）
- **首页内容列刻意只有 480px**（贴近手机 430）——首页 `l1` 是 6 列 grid，卡片会随容器等比放大，
  限宽太大会把高度撑出一屏 → 违背"主页面不用滚动"的硬要求。聊天/设置/字卡等纵向滚动页才用 640/680
- 用户之前拍过板：电脑端 **viewport 铺满整个窗口**，不要回到"居中窄竖屏卡片" → 只限宽内容，viewport 保持铺满

### 已落地（style.css 末尾 @media(min-width:768px)）
- 四个可调变量：`--desk-home:480px` / `--desk-chat:680px` / `--desk-panel:640px` / `--desk-dock:520px`
- **滚动容器**（.chat-flow/.deck/.settings-scroll/.board-list）用 `padding-inline: max(14px, calc((100% - var(--desk-*)) / 2))`
  而不是 max-width+margin —— 这样滚动区仍满宽、滚动条贴屏幕边缘，不会跑到屏幕中间
- **非滚动容器**（.l1/.l2/.dock/.board-input/.input-style-N/toolbar）才用 `max-width + margin-inline:auto`
- 桌面端显示 6px 细滚动条（手机端仍 display:none）、补 hover 反馈、表情包墙 8 列
- 追加 `@media(min-width:768px) and (max-height:820px)`：压首页留白，应对 1366×768 只剩 ~640px 视口高的情况

## ⚠ 电脑端布局：最终拍板 = 保留「居中手机壳」，不要铺满

用户试过铺满全屏后要求**恢复最初的样子**。所以 `@media(min-width:768px)` 里**不再**有生效的
`.viewport{...}` 规则（只留注释版备用）。电脑端最终生效链：
```
基础      .viewport { width:100%; max-width:430px; height:100dvh }
≥480px    .viewport { height:94vh; border-radius:32px; box-shadow:0 30px 80px rgba(0,0,0,.5) }
≥600px    .viewport { width:460px; margin:0 auto }   ← 被基础 max-width:430 截断，实际壳宽仍是 430
```
壳外背景 = `body{background:#111; display:flex; justify-content:center; align-items:center}`
**别再给它加 width:100%/max-width:none** —— 要调宽壳得同时改基础的 `max-width:430px`。

768 块里现在只剩「交互增强」（细滚动条 6px、鼠标 hover 反馈）和一组 `--desk-*` 限宽变量
（430 壳下全部不生效，仅作将来改宽/改回铺满时备用）。被撤掉的：viewport 铺满、表情包 8 列、tab 栏居中。

## 首页「不滚动」= 内容整体等比缩放（fitHome）

用户诉求：首页不想滚动。

### 实现（app.js）
- `cfg.fitHome`（默认 true，DEFAULTS.cfg 里加的）；UI 开关在设置页「主页」tab → 首页高度 → `sw_fitHome`，走 `cfgToggle('fitHome')`
- `fitHomeToScreen()`：量 `.home-scroll` 的 `clientHeight` vs 内层 `.l1/.l2` 的 `scrollHeight`，
  超出就 `transform: scale(k)`，`transform-origin: top center`（CSS 里给 `.home-scroll > *` 设的）
- `k < FIT_HOME_MIN(0.62)` 时钳到 0.62 并放行 `overflow-y:auto` —— 宁可滚也不裁内容
- `fitHomeWatch()`：`ResizeObserver` 观察 `.home-scroll > *`（改文案/换图/字号都会触发）+ window resize 防抖 120ms
  ⚠ 不会自循环：RO 看的是布局尺寸，transform 不改布局尺寸
- 调用点：`init()` 里 `renderMembers()` 之后；`syncUI()` 里（setSw 之后）——所以切布局/改字号/开关后都自动重算
- CSS：`.viewport[data-fit="1"] .home-scroll { overflow-y: hidden }`，data-fit 由 syncUI 写在 `#vp` 上

### 可调的旋钮（别的地方别乱动）
- `FIT_HOME_MIN = 0.62`：嫌缩太小就调大（如 0.75），代价是更早放行滚动
- 不想缩放、想靠减内容解决：调设置里的字号，或改 `@media(min-width:768px) and (max-height:820px)` 里的 padding/gap
- 桌面端首页宽度 `--desk-home:480px`（越宽卡片越大、越高，越容易超出一屏）
